## 六、评审意见裁定（滚动追加，每条给原文证据）

### 6.1 产品经理提的两处（`docs\relay-tool-params-pm-20261119.md`，65 行 / 6,753 B）

**① body 上限 4,000 → 3,800：不采纳。**

- 事实：`DEFAULT_INLINE_MAX_CHARS = 4000`（`index.js:23`）管的是**注入消息里内联多少字**，不是文件大小上限；文件永远落全文。超限时 `inlineBodyOf` 只回落成一句「（正文 N 字节，超过内联上限 4000 字符，未内联；请读上方路径）」（`index.js:938-943`），正文仍在磁盘上。
- 若把 body 限到 3,800，等于让工具**拒收长正文**，长件连落盘都做不到，比现在多读一次更差。
- 签名口径：工具不设字符上限，只设防误用的字节护栏（建议 1 MiB，超限 `ok:false` 并给 `E_BODY_TOO_LARGE`＋当前字节数）；`inline` 是否截断由既有 `inlineMaxChars` 决定，工具返回里带 `inlined: true|false`，让调用方知道要不要让目标再读一次。

**② body 内的 `From:`／`To:` 行必须剥：采纳，但剥的位置要提前。**

- 事实：现有 `stripIdentityLines`（`index.js:882`）只在**注入侧**剥（`inlineBodyOf` `:932`、`buildMessage` `:959`），落盘文件里仍保留调用方塞进来的 `From:`／`To:` 行；机检「首个头胜出」时那就是伪造入口。
- 签名口径：工具在**写文件之前**对 body 调 `stripIdentityLines`，注入侧保持现有剥离（双保险）；单测加两类样本——body 含一行 `From:`、body 含三行 `To:`，断言文件与注入消息各恰好一行头，且外层头的 sender 是真实调用会话。

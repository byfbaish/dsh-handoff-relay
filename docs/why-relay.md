# 为什么叫 relay

## 一、一个被误认为「夺舍」的瞬间

界面给了我一个错觉：项目群里的那个助手，和我私聊窗口里的那个助手，看起来是同一个——同一个名字，同一张脸。

直到我想让它随时能找到我，这个错觉才破。它们是两个会话，两个不同的 session id，上下文互不相通；唯一的共同点，是共享同一份记忆。

真正让我看到「撕裂」的是权限：通知工具只允许私聊那个发消息。界面上的同一性，到这里彻底断了——我第一次意识到，它们从来不是同一个。

于是我搭了两道桥。

第一道是外挂记忆：一个 Markdown，写进它记忆里的只有一个索引，具体的事都在这个文件里。两个会话读同一份文件，就有了同一个大脑的两半。

第二道是跨会话投递：我们那晚正在做的那个插件——一个目录对一个会话，文件写完、尾部出现约定标记，就把一句话送到另一个会话。那时它还没接好，我本来只想提醒它一句：这个正好能当桥。

可那条消息被网络吃掉了，没发出去。

它没有等我。它自己发现这个插件正好能当桥，自己判断这条路走得通，自己排了验证，然后把整条链路跑通了。插件是人做的；它做的是「看见这里能用，并证明它能用」。

桥通了之后出过一次事故，也是这个项目最值钱的一条经验：投递的那句话只带了文件名、没带路径。接收的一侧工作目录不同，找不到文件，连收两条之后，它的判断是——这不是正常通知，我的输入可能被塞了东西。当时的形容是：像被夺舍。它没有照着执行，而是先停下来问发生了什么。

现在那句话带绝对路径。

## 二、怎么修的

三处改动，都指向同一个原则：把不确定性留在发送端，不要留给接收端。

**通知带绝对路径。** 原来的通知只写文件名，收件方只能在自己的工作目录里凭名字找。文件一旦被清理，就找不到；找不到就会怀疑通知本身有问题，甚至去查是不是有探针在反复触发。现在通知里直接给出被投递文件的绝对路径，收件方按路径读，不必猜，也不会因文件消失而误判来源。

**会话寻址按标题包含匹配。** 会话 id 在宿主新建会话时会变，写死 id 的配置每次重启都要重新接线。标题更稳定，也更好核对。匹配用子串而不是全等：「简报」能命中「周简报」，因为人写标题时往往带修饰。但匹配必须恰好命中一个会话。

**解析不到就跳过并告警。** 命中零个或多个，都不投递，只写一条能看出是哪条监控项、找的是什么标题、命中几条的警告。绝不按工作目录去猜「最近活跃的那个会话」——发错比不发更麻烦：一条发错的通知会在另一个会话里制造新的、无法解释的上下文，正好复现第一节那种误判。

## 三、多播：想到了，但先不做

多播的想法很自然：一个文件就绪，同时唤醒好几个会话，像一根神经末梢把信号分发给多个突触。

暂缓的理由也很直接。第一，同一目录投给多个目标，现在就能用多条监控项表达，语义清楚，无需新机制。第二，一旦允许「一个事件唤醒 N 个会话」，投递层就得决定「谁该被唤醒、按什么顺序、失败了怎么办」——这是编排，是 agent 层的职责。投递层只该回答一个问题：这条消息送给谁。把编排塞进来，边界就糊了，而边界糊掉的代价是行为不可预测。

## 四、这个插件的边界

它只做一件事：判定文件是否写完，然后把一条消息投给指定的那个会话。

不读文件内容（只扫尾部字节找完成标记），不维护跨文件的状态机，不执行命令，不编排多个目标。名字里的 relay 就是这个意思：把「已就绪」的信号点到点转达到一个会话。

边界窄，行为才可预期。误判大多发生在边界被悄悄拓宽的地方。
